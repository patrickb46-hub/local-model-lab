# 本地模型实验室 · Local Model Lab

> **一个 base，两条支线**：同一份 Qwen3.5-2B 复制成两份互不干扰的副本 ——
> 一份吃蒸馏（向本机 9B teacher 学），一份吃强化学习（GRPO）。
> 最后用同一套数学小题横评 base / 蒸馏产物 / RL 产物 / teacher。

完整设计与取舍见 [`完整计划.md`](完整计划.md)；这一份是**快速上手 + 现状**。

> **不想看技术细节？** 打开 [`项目全貌.html`](项目全貌.html)（或 [`项目全貌.md`](项目全貌.md)）——
> 那是给非技术读者写的，用打比方的方式讲清楚这个项目在做什么、结论是什么。
> 想直接看实验结论：在 **teacher 自己也不会做的题（L2）上，RL 臂做到 56.2% 而蒸馏臂只有 16.7%**。

## 一、当前的系统定位（重要）

这台机器是 **2018 款 Intel MacBook Pro（x86_64）**，这部分硬件条件塑造了整个项目的技术选型。
如果你在另一台机器上照着跑，先读 [`docs/踩坑记录.md`](docs/踩坑记录.md)，那里有六个会让整条管线卡死的坑。

| 项 | 现状 |
|---|---|
| 架构 | x86_64（Intel）—— **没有 MPS，只能纯 CPU** |
| 内存 | 16 GB（系统先占 4–6 GB） |
| 训练解释器 | `envs/mlab-conda/bin/python`（conda-forge 提供现代 torch） |
| base 模型 | `Qwen/Qwen3.5-2B`（HF 格式，约 4.6 GB） |
| teacher | 本机 Ollama `qwen3.5:9b`（只动嘴，绝不训练） |

### 为什么有两个 Python 环境

这是个绕不开的矛盾，值得单独说清楚：

```
Intel Mac 的 PyPI torch  → 停在 2.2.2（之后官方不再发 macOS x86_64 轮子）
Qwen3.5 需要 transformers  → 5.x（4.57 里根本没有 qwen3_5 架构）
transformers 5.x 要求      → torch >= 2.5
                          ↑ 三者不能同时成立
```

出路是 **conda-forge**：它给 osx-64 一路编到了 `pytorch 2.13.0`（含 `cpu_mkl_py312` 构建）。
所以最终环境是这样的：

| 环境 | 用途 | 内容 |
|---|---|---|
| `envs/mlab-conda` | **主力**：所有需要模型的脚本 | conda-forge python 3.12 + pytorch 2.13.0(MKL) + pip 装的 transformers 5.x / peft |
| `envs/mlab` | 备用：不需要模型的脚本 | 纯 PyPI，torch 2.2.2（能跑但带不动 Qwen3.5） |

脚本通过 `configs/lab.config.json` 的 `runtime.python` 指向主力环境，
`common.resolve_python()` 会在它不存在时自动降级。

## 三、统一任务轴

两条支线跑在**同一个任务**上，这样横评才有可比性：

> **初中数学小题 · 结构化分步解答**

固定的输出格式（机器可解析）：

```
【思路】用一句话点明解题方向。
【步骤】
1. 第一步……
2. 第二步……
【答案】只写最终答案。
```

题源由 `09_gen_math_bank.py` **程序化生成**（十个类别，答案用 `Fraction` 精确运算）。
选程序化出题而不是手写题库，理由很直接：

- 答案天然精确 —— 强化学习才可能有"可验证奖励"，不需要额外训练奖励模型
- 可固定种子复现，可无限扩样
- 题目与答案严格一一对应，不留"标准答案靠猜"的模糊地带

| 支线 | 学什么 | 奖励 / 监督信号 |
|---|---|---|
| A 蒸馏 | 数学分步解题的表达 + 固定格式（A2 领域 + A3 格式） | 模仿 teacher 的回答（token 级监督） |
| B 强化学习 | 数学小题 + 领域输出规范（B3 + B4） | 答案正确 +1.0 / 格式合规 +0.5 / 步骤齐全 +0.2 / 答案超长 −0.3 |

## 四、跑起来

所有脚本都用 `python scripts/xx.py` 运行。**按编号顺序**：

| 步骤 | 脚本 | 作用 | 耗时量级 |
|---|---|---|---|
| 0 | `00_check_env.py` | 环境自检，全绿才往下走 | 秒级 |
| 0 | `01_setup_env.sh` | 搭建 Python 环境（幂等，可重复跑） | 十几分钟 |
| 0 | `02_download_base.py` | 从 hf-mirror 下载 base 权重 | 十几分钟 |
| 0 | `03_make_copies.sh` | 复制成两份隔离的工作副本 | 1 分钟 |
| 1 | `09_gen_math_bank.py` | 生成题库 + 锁定评测集 | 秒级 |
| 1 | `10_gen_distill_data.py` | teacher 批量生成蒸馏数据 → 清洗切分 | 1–3 小时 |
| 1 | `11_train_distill.py` | LoRA 监督微调 | 2–4 小时 |
| 2 | `20_train_rl.py` | GRPO 强化学习 | 1–3 小时 |
| 3 | `30_evaluate.py` | 四模型横评 | 几十分钟 |

### 一键夜间批处理

想省事就一条命令，它会按顺序把上面全部跑完（两条支线**严格串行**，绝不同时占机器）：

```bash
cd ~/Desktop/AI/Local-Model-Lab
nohup bash scripts/99_night_run.sh > /dev/null 2>&1 &
```

它做了三件让人省心的事：

1. **`caffeinate` 全程顶着** —— macOS 睡眠会掐断长任务（下载模型时踩过），必须钉住
2. **每步幂等可续跑** —— 中途断了重新执行本脚本，已完成的会自动跳过，不会白干
3. **全过程写进 `logs/night_run.log`** —— 早上起来只看这一个文件

### 随时查进度 ← 最常用的命令

**想知道"现在跑到哪" → 只看 `progress.sh`**（唯一入口，一屏看完）：

```bash
cd ~/Desktop/AI/Local-Model-Lab

bash scripts/progress.sh             # 中文，看一次
bash scripts/progress.sh -w          # 每 20 秒自动刷新（Ctrl-C 退出）
bash scripts/progress.sh -w 5        # 自定义刷新间隔为 5 秒

bash scripts/progress.sh --en        # 英文版
bash scripts/progress_en.sh          # 英文版（同上，省一个参数）
bash scripts/progress_en.sh -w       # 英文 + 自动刷新
```

它显示：**正在跑什么**（哪些进程活着）、**全流程时间线**（P3~P7 每一步的耗时）、
**四个臂的产物**（A1/A2/B/C 的 adapter 大小）、**数据产物**、
**评测进度 · 主测按层**（哪个角色哪一层还差多少）、
以及 **GATE-1 闸门判定**（L2 题够不够 24）。

**耗时一律自动进位**，不再是一长串秒：`25549s` 显示成 `7h05m`，
`5230s` 显示成 `1h27m`，超过一天则进位到 `1d01h`。

专用查看器（按需）：

| 命令 | 看什么 |
|---|---|
| `bash scripts/progress.sh` | **全流程**（推荐，就是上面这个） |
| `bash scripts/screen_status.sh` | 分层筛查（P2）的细节：base/teacher 进度、难度分布、ETA |
| `bash scripts/watch.sh` | 上一次「夜间批处理」的步骤时间线（**日志陈旧时会警告**） |

**`watch.sh`** 是一眼看清"跑到哪、还剩多久"的查看器（只读，随时可跑）：

```bash
cd ~/Desktop/AI/Local-Model-Lab

bash scripts/watch.sh              # 中文快照
bash scripts/watch.sh --en         # 英文快照（界面全英文）
bash scripts/watch.sh --both       # 中英各一份，分开两段
bash scripts/watch.sh -w           # 每 20 秒自动刷新（Ctrl-C 退出）
bash scripts/watch.sh -w 5         # 自定义刷新间隔为 5 秒
bash scripts/watch.sh -w --en      # 可组合：英文 + 自动刷新
```

渲染逻辑单独放在 `scripts/watch_render.py`（避免大段代码塞进 shell 时的引号问题），
`watch.sh` 只负责参数解析与刷新循环。

它输出：步骤时间线（哪几步已完成、各自耗时）、当前步骤的进度条与 ETA、
两条支线的 loss / adapter 状态、**预计全部完成的时间**，以及资源占用。

**⚠ 它只认「夜间批处理」的日志**（`logs/night_run.log`）。
那个日志记录了上一次完整流程 —— 如果它已经很久没更新，屏幕上会显示
「全部完成」，但那是**历史记录**，不是当前进度。为此 `watch.sh` 现在会在
日志超过 24 小时未更新时打印醒目提醒，并指向下面这个脚本。

### 要用电脑干别的事 → 暂停 / 恢复 ← 用 `labctl.sh`

实验进程常驻约 12GB 内存。想临时把机器让给自己用：

```bash
cd ~/Desktop/AI/Local-Model-Lab

bash scripts/labctl.sh status            # 现在在跑什么、到哪了（只读，随时可跑）
bash scripts/labctl.sh pause             # 暂停：停掉全部实验进程，释放内存
bash scripts/labctl.sh resume            # 恢复：接着上次的进度继续跑
```

**为什么暂停是安全的**：评测**每条样本落盘即视为完成**，重启时按键
`(角色, 题号, kind, 采样序号)` 自动跳过 —— 最坏只丢「正在生成的那一题」，
恢复时会自动重跑它。

> 实测演练过：暂停前 A1 是 84/156，恢复后日志显示 `[21/52]…[28/52] 全 0s`
> （自动跳过已完成的 8 题），从第 29 题继续；654 条记录**零重复、零损坏**。

**三个必须知道的点**：

| 情形 | 说明 |
|---|---|
| **训练期间暂停** | **不是无损的**。SFT / RL 每 5 步存一次 checkpoint，会丢掉自上个 checkpoint 以来的步数。脚本会拒绝，要求你确认 `pause --force` |
| **恢复请在你自己终端里跑** | 这样启动的进程属于你的登录会话，比工具托管的更不容易被回收 |
| **自动巡检会自动让路** | `pause` 会建一个 `logs/PAUSED` 标记，每 2 小时的自动巡检看到它就**什么都不做** —— 否则它会把你刚暂停的东西重新拉起来，正好打断你 |

暂停时还会把评测原始记录留底到 `logs/eval_raw_before_pause.jsonl`（几十 KB），
想回退时有个参照。

### 看正在跑的分层筛查 ← 用 `screen_status.sh`

```bash
bash scripts/screen_status.sh        # 看一次
bash scripts/screen_status.sh -w     # 每 20 秒刷新
bash scripts/screen_status.sh -l 20  # 附带最近 20 行日志
```

它专看 **P2 分层筛查（GATE-1）**：进程状态、base/teacher 各完成多少题、
**base 侧难度分布**（全错 / 部分对 / 全对 —— 其中「部分对」是 L2 候选池）、
速度与 ETA，以及跑完后的**闸门判定**（L2 是否够 24 题）。

### 中断了怎么办 ← 别直接重跑 99_night_run.sh！

**这是最容易踩的坑**：`99_night_run.sh` 里的训练步骤为了保住受控变量用了
`--fresh`（强制从零开始训）。所以直接重跑它，会**重新训练 A（约 2.2 小时）+ B（约 5 小时）**，
白烧一晚，还会覆盖已经训好的 adapter。

改用 **`resume.sh`** —— 它按日志里的 `◀ 步骤名 … 退出码=0` 完成标记判断，
已完成的训练直接跳过，只补没跑完的：

```bash
bash scripts/resume.sh --dry-run    # 先看它打算做什么（安全，不动机器）
bash scripts/resume.sh              # 确认后补跑
```

它还会先检查有没有别的进程在跑，避免两个流程抢内存。

早上看结果：

```bash
tail -100 logs/night_run.log        # 全过程与每步耗时
python scripts/31_report.py --open  # 打开可视化横评报告
```

### 先跑探针，再放全量

CPU 上最贵的失败方式是"跑三小时然后爆内存"。所以两个训练脚本都有探针模式：

```bash
python 11_train_distill.py --probe     # 跑 3 步，报每步耗时 / 峰值内存 / 全量 ETA
python 20_train_rl.py --probe          # 跑 1 步，报同样信息
```

**建议节奏**（计划里也是这么写的）：先跑阶段 0 → 再用最小规模把支线 A 走通
（`--limit 20` 生成数据、`--epochs 1 --limit 40` 试训），确认整条管子通了，
再放开全量、再复制经验到支线 B。**第一次跑，先求通，再求好。**

### 长任务的现实

本机上下文里有个反复踩过的教训：**会话结束或模式切换时，后台进程会被回收**。
所以：

- 每个长任务脚本都做了**断点续跑**（`10_gen_distill_data.py`、`30_evaluate.py`
  每条结果即时落盘，重跑自动跳过已完成项）
- 中途断了直接重跑同一条命令即可，不会白干
- 跑之前先插电、关掉 Spotlight 索引之类的后台负担

## 五、评测口径

**六模型跑同一套 `shared/eval_set.jsonl`**，按五个维度看：

| 列 | 是谁 | 来源 | 回答什么问题 |
|---|---|---|---|
| `base` | Qwen3.5-2B 原版（HF 权重） | 本地 | 起点 |
| `A` | 2B + 蒸馏 LoRA | 本地 | 蒸馏赚了多少 |
| `B` | 2B + RL LoRA | 本地 | RL 赚了多少 |
| `dsv4pro` | DeepSeek V4 Pro | **云 API** | **离真正的强模型还差多远** |
| `qwen4b` | 官方 `qwen3.5:4b` | Ollama | **微调后的 2B 能不能追上原版 4B** |
| `teacher` | 官方 `qwen3.5:9b` | Ollama | 天花板 |

> 原 `qwen2b`（官方 `qwen3.5:2b` 量化版）**已移出**：它与 `base` 是同一个模型的两种精度，
> 差异只反映量化损失、不反映能力，留在表里反而干扰读表。
> 去掉后改用**云 API 强模型**补位 —— 前 6 个角色里有 5 个都是 Qwen 系、3 个是量化版，
> 仅靠它们无法回答"离真正的强模型还有多远"。

每个模型还要跑**两个 thinking 条件**：关闭（主测，完整口径）与开启（小题量对照探针）。
开思考时输出会长好几倍，本机 1.32 tok/s 下不控量跑不完，所以对照只作趋势参考。
判分前**必须先剥掉推理块** —— 模型在推理里也会写出格式标记，不剥离会把"自言自语"当成正式答案。
（本地/Ollama 走 `<think>` 标签解析；云 API 的推理内容是**独立内容块**，按块类型挑即可。）

⚠️ **各角色的 token 预算不同，`think=开` 那一栏不能横向比较**：
本机角色是 192 / 384，云角色是 1024。192 这个上限是为「纯 CPU 一条要 40–90 秒」定的；
云 API 一条只要几秒，把本机的硬件限制套到云基线头上会造成"被截断的假性低分"。

其中 `base / A / B` 是**同一份 2B 权重 + 不同 LoRA 适配器**，靠 PEFT 多适配器切换扮演三个角色
（省下两份权重的内存）；`qwen4b` / `teacher` 走本机 Ollama；`dsv4pro` 走网络。
**密钥只以环境变量名写进 config（`api_key_env`），任何文件里都不落密钥。**

| 指标 | 测什么 | 谁最该看 |
|---|---|---|
| 格式遵从率 | 【思路】/【步骤】/【答案】三段齐全且顺序正确 | RL |
| 任务正确率 | 【答案】与程序生成的 ground truth 是否等价 | 两条都看 |
| 与 teacher 一致性 | 输出与 9B teacher 的相似度 | 蒸馏 |
| 输出多样性 | 有没有训崩（输出趋同） | RL 重点 |
| 通用能力保持 | 闲聊 / 常识小测，盯灾难性遗忘 | 两条都必测 |

**口径细节**：
- 主测用**温度采样（T=0.7）× 每题 3 次重复**，报告「均值 ± 标准差」。
  **为什么不用 greedy(T=0)**：它是确定性的，重复跑结果完全一样、取平均毫无意义 ——
  想用"多次实验取平均"降误差，就必须用随机采样。同一批 3 次采样**兼用于**算输出多样性，
  不必另跑一轮。
- 答案比较做了归一化：全角转半角、去 LaTeX 装饰（`\boxed{}`/`\frac`）、去单位、
  分数 / 小数 / 带分数等价比较。
- **格式遵从率与答案正确率是两个独立指标**：判分器带一层"兜底答案提取"，
  让没学过本格式的官方模型（写「答案是 2」而非`【答案】2`）也能被正确判分 ——
  否则会把"不守格式"误算成"答错"，得出"微调后的小模型碾压官方模型"这种**方向性错误的结论**。
- 训练与评测生成统一 `float32`（本机 fp32 在训练和生成两个方向上都胜过 bf16，
  理由见 [`docs/踩坑记录.md`](docs/踩坑记录.md) 坑 9）。

### 一个必须知道的实测发现：teacher 自己会答错

实测官方 `qwen3.5:9b` 在这套算术题上**错误率约 20%**（已手工验算确认是它算错，不是判分器误判）。

所以蒸馏数据默认启用**验证筛选**（`distill.filter_correct = true`）——
用同一个判分器把答错的样本剔除，否则学生等于在学错的解法。

**这样两条线仍然公平**：支线 B 的奖励用的是同一个验证器，两条支线都吃"题目可验证"这个前提，
谁也没占额外便宜。想对比"不过滤的朴素蒸馏"，把该开关置为 `false` 重跑即可。

### 受控变量

两条支线对齐到**相同的优化步数（60 步）**。原因是两者单步成本天差地别
（实测：SFT 一步 **127.5 秒**；GRPO 一步约 **320 秒**，要跑 4 次完整生成）。
若按墙钟时间对齐，同样的 5.5 小时里 SFT 能跑约 154 步而 GRPO 只有 60 步 ——
那就变成比预算而不是比方法了。

两个必须遵守的配套约定：
- **正式训练一律加 `--fresh`**。否则会继承探针留下的 adapter，实际变成「66 步 vs 60 步」，
  受控变量静默失效（踩过：日志里 `计划优化步数 28` 就是没对齐的证据）。
- **`num_epochs` 要够大**，否则 `max_steps=60` 够不到：110 条样本 ÷ accum 8 = 14 步/轮，
  2 轮只有 28 步就被数据耗尽截断。

## 六、明确不做的事

- ❌ **不训练 9B** —— 内存物理上不够，任何形式都不行
- ❌ **不做全参数微调** —— 只走 LoRA
- ❌ **不做 logit 级蒸馏** —— teacher/student 同时驻留需要约 23 GB，超物理内存，走序列级
- ❌ **不追求 benchmark 高分** —— 2B 在大 benchmark 上没有区分度，自建测试集更有效
- ❌ **不用闭源 API 的输出做训练数据** —— 合法性的真正红线在这
- ❌ **不指望「微调能把 2B 变成 4B」** —— 微调不增加参数量。LoRA 只加 0.9%（16.8M）
  的旁挂参数，合并后仍是 2.21B。想得到 4B 产物必须以 4B 为底座，
  而 4B 的 fp32 权重就要 17.5 GB > 本机 16 GB（详见 `docs/踩坑记录.md`）
