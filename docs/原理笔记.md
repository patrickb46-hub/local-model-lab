# 原理笔记

> 记下这个项目里几个"为什么这么做"的技术判断。
> 目的不是科普，而是把当时的选择和它的代价钉住，将来回头看能有据可依。

---

## 一、为什么是「序列级蒸馏」而不是 logit 级

蒸馏分两档：

| | logit 级 | 序列级（本项目） |
|---|---|---|
| 监督信号 | teacher 每个位置的完整概率分布 | teacher 最终生成的文本 |
| 信息量 | 大得多（含"软标签"和类间相似度） | 少（只有"最优路径"） |
| 内存 | teacher + student **同时驻留** | 只要 student 驻留 |
| 本机可行性 | 9B + 2B ≈ **23 GB** > 16 GB ✗ | ✓ |

**判断**：logit 级确实更强，但在这台机器上它需要同时把两个模型塞进 16 GB，
物理上不可能。所以退到序列级：**teacher 先把答案写成文本，student 再模仿文本**。

代价很明确 —— 丢了概率分布里的"暗知识"。但换来的是这条管线**真的能跑**。
在"跑得通"和"理论上更优"之间，16 GB 内存没给我们选择的余地。

## 二、GRPO 为什么比 PPO 省内存

这是 RL 支线能启动的关键。

**PPO** 需要三样东西同时驻留：

1. 策略模型（policy）
2. 参考模型（reference，算 KL 用）
3. **价值模型（value model，估优势用）**

第 3 项是个和策略**同规模**的模型 —— 2B 再来一个，内存直接翻倍。

**GRPO 的做法**：不要 value model。同一道题采样一组（G 个）答案，
**用组内的相对好坏**当基线：

```
A_i = (r_i − mean(r)) / (std(r) + ε)
```

奖励高的答案被强化、低的被抑制，基线由同组答案自己提供。
省掉一个 2B 模型，这是 GRPO 在这台机器上唯一的立足点。

**参考模型怎么办**：我们本来以为要再加载一份权重算 KL。实际上不用 ——
LoRA 训练时**关掉适配器就是原始策略**，所以用同一份权重、切换适配器状态即可，
**零额外内存**：

```python
with model.disable_adapter():        # 关掉 LoRA = 回到参考策略
    ref_logp = ...
```

KL 用 **k3 估计量**（无偏低方差）：

```
KL ≈ E[ exp(ref_logp − logp) − (ref_logp − logp) − 1 ]
```

它的好处是：当 policy 和 reference 完全一致时，每项恰好为 0，
不会有 k1 那种"恒正偏差"把 KL 项虚高。

## 三、LoRA 的选择与代价

**为什么只训 LoRA**：2.3B 参数在 fp32 下权重就 9.2 GB。
全参微调还要加上梯度（又一个 9.2 GB）和 AdamW 的两个动量（再 18.4 GB）——
37 GB，完全不可能。

LoRA 把这变成：**冻结全部原始权重，只训两个低秩矩阵**。
`r=16` 时，可训练参数不到总量的 0.5%，优化器状态可以忽略。

**代价**：表达能力受限，学不到"深层的表征改变"，只学到"行为层面的调整"。
在对齐 / 格式 / 解题套路这类任务上够用；要它学会一门新语言就不够。

**本项目的特殊之处**：Qwen3.5 是混合注意力架构（线性注意力 + 每 4 层一个 full attention），
层名不遵循 `q_proj/k_proj/v_proj` 的惯例，所以 `target_modules` 必须**运行时探测**
而不是照抄教程：

```python
suffixes = sorted({name.split(".")[-1] for name, m in model.named_modules()
                   if isinstance(m, nn.Linear)})
```

探测时还要排除 vision 与 MTP 相关的层。

## 四、判分器：整条评测链路的地基

如果判分器不可靠，后面所有数字都没有意义。所以它值得单独设计。

### 4.1 答案等价，而不是答案相等

模型会写 `3/4`，也可能写 `0.75`、`\frac{3}{4}`、`0.75元`、全角数字。
所以比较前要归一化：

1. 全角 → 半角（含 `１２３` → `123`、`（）` → `()`）
2. 去掉 LaTeX 装饰：`\boxed{}`、`\text{}`、`$...$`、`\frac{a}{b}` → `a/b`
3. 砍掉"答案 / 答 / 所以 / 故"这类前缀
4. 去尾部句号、去空白
5. 数值统一用 `Fraction` 比较（`3/4 == 0.75` 为真），带分数 `1又1/2` 也要认
6. 单位后缀（元 / 厘米 / 度…）一律剥掉后比较

**这一步做不扎实，就会出现大量"假错误"** —— 模型明明答对了，
却因为写成了 `0.75` 而标准答案是 `3/4` 被判错，最后得出一堆错误结论。

### 4.2 格式合规是硬判定

固定格式：

```
【思路】…
【步骤】
1. …
【答案】…
```

判定条件是**三段齐全且顺序正确**（`idx(思路) < idx(步骤) < idx(答案)`）。
不是"包含就行" —— 顺序错了说明模型没真正理解结构。

### 4.3 奖励为什么全是可验证的

```
答案正确   +1.0     ← 与程序生成的 ground truth 比对
格式合规   +0.5     ← 三段齐全且有序
步骤齐全   +0.2     ← 至少一个编号步骤
答案超长   −0.3     ← 惩罚把答案区写成一整段废话
```

四项都能用程序判定 → **不需要训练奖励模型** → 又省掉一份权重。
这是"程序化出题"这个决定的直接红利：题目由程序生成，答案天然精确，
奖励才能做到全可验证。

### 4.4 为什么多样性要单独测

RL 有个典型的失败模式：**奖励涨了，但模型学会了套模板**。
正确率上去了，输出却千篇一律 —— 从"会做题"退化成"会填格式"。

所以多样性必须**用高温多次采样单独测**（同一题采 3 次，算两两差异度的均值），
而不能从 greedy 的结果里推。greedy 每次都一样，看起来"多样性"是 0，
但那不是信息 —— 必须让模型有机会表现出分歧。

同理，正确率与格式遵从率用 **greedy（温度 0）** 测，
因为要的是"稳定命中率"而不是"运气好一次"。

## 五、纪律：为什么评测集必须提前锁死

`shared/eval_set.jsonl` 在**训练开始前**生成并冻结，且**永不进入训练数据**。

这不是洁癖。如果评测题混进训练集，模型会把答案背下来，
最终数字会好看得离谱 —— 但那是记忆，不是能力，整个横评失去意义。

所以代码里做了硬校验：

- 题库生成时严格三段切分（eval / 蒸馏 / RL），断言三者 id 集合两两不相交
- `10_gen_distill_data.py` 清洗完还再查一遍题面是否与 eval 撞题，撞了就剔除
- `00_check_env.py` 把三条不相交断言做成环境自检的一部分

**这条破了，后面所有结论都不用看了。** 所以宁可让它在流程里"挡路"。

## 六、训练超参的取舍

| 参数 | 取值 | 理由 |
|---|---|---|
| `per_device_batch_size` | 1 | CPU 上基本锁死，没有余地 |
| `gradient_accumulation` | 8 | 用 1 的小批拼出等效批 8，降低梯度噪声 |
| `max_seq_length` | 512 | **内存的主要开关**。数学小题 + 分步解答这个长度够用 |
| `learning_rate` | 1e-4（SFT）/ 5e-5（GRPO） | LoRA 的常用区间；RL 更保守，防止训崩 |
| `lr_schedule` | 线性 warmup + 余弦衰减 | warmup 防早期震荡，余弦让后期稳下来 |
| `gradient_checkpointing` | 开 | 拿时间换内存。CPU 上时间本来就便宜，内存才是瓶颈 |
| `lora_rank` | 16 | 再大表达力更强但更容易过拟合到格式；数据只有 200 条，16 够 |
| `kl_coef` | 0.02 | 太小则跑飞，太大则学不动。先小步验证趋势 |

**核心原则**：在这台机器上，**内存是硬约束，时间是软约束**。
所有取舍都朝"更省内存、更慢一点也行"的方向偏。

## 七、算力量级（估算，供排期参考）

实际取决于当次机器状态（后台进程、温度、磁盘 IO 都会影响）：

| 环节 | 量级 |
|---|---|
| 下载 2B 权重（4.6 GB，hf-mirror） | 十几分钟 |
| teacher（9B）生成 200 条数据 | 1–3 小时 |
| 蒸馏训练（200 条 × 3 轮，CPU） | 2–4 小时 |
| GRPO 训练（30 步左右） | 1–3 小时 |
| 四模型横评（30 题 + 多样性子集） | 几十分钟 |

**唯一正确的开工方式**：先跑 `--probe` 拿实测数（每步耗时 / 峰值内存 / ETA），
再决定放开多少量。不要凭估算直接开全量。
