> 这份文档**不是坑的清单**（那是 [`踩坑记录.md`](踩坑记录.md) 的活），
> 而是从那 24 个坑里**提炼出来的、可以带到下一个项目的原则**。
>
> 项目背景：2018 款 Intel MacBook Pro（无独显），纯 CPU 上做 Qwen3.5-2B 的
> 蒸馏与强化学习对照实验。两轮完整实验、约 40 小时机器时间。

## 零、三条元规律

24 个坑，绝大多数可以归到下面三条。**先记住这三条，比记住 24 个细节有用。**

### 元规律 1 · 沉默的错误比崩溃危险得多

崩溃会留下堆栈，而沉默的错误只留下**看起来很正常的垃圾数据**。

本项目里最贵的三次事故全是这一类：

| 事故 | 表面现象 | 实际后果 |
|---|---|---|
| Ollama 挂掉，145 条调用失败被记成「答错」 | 日志一行错误都没有 | 整个分层基准作废 |
| `[:20]` 截断遇上按层分块写入 | 报告照出、图表照画 | 评测集里只剩一层，核心问题无法回答 |
| 守护进程判据写死 | 守护"安静地不干活" | 3.5 小时补跑全程无保护 |

**可迁移的检查动作**：
任何跨越数小时的长任务，在设计时先问一句 ——
**「如果这一步悄悄失败了，我多久之后才会发现？靠什么发现？」**
如果答案是「几小时后看结果时，而且要靠数字自相矛盾才发现」，那就必须加保护。

### 元规律 2 · 写死的假设，会在系统变复杂时失效

- 「评测集就是那 20 题」→ 换了分层基准之后，`[:20]` 的意思完全变了
- 「主流程就是 97 脚本」→ 加了 98 补跑脚本之后，守护立刻失效

**两种失效都发生在「加了一个新东西、但旧代码里有个针对旧东西的写死假设」的时候。**
加新组件时，**回头检查所有「假设了只有一个」的地方**：
只有一个脚本、只有一个日志、只有一种格式、只有一个输出目录。

### 元规律 3 · 工具比记忆可靠

同一个错误（`$VAR` 紧跟全角标点导致 unbound）**犯了 7 次**。

第 1–6 次都是靠"记住下次注意"，第 7 次**是 `lint_shell.sh` 抓到的**。
写一个五行脚本能永远防住的事，不要指望意志力。

**可迁移的检查动作**：发现自己同一个错误犯第二遍时，**立刻写个检查脚本**，
而不是提醒自己"下次小心"。

## 一、实验设计

### 1.1 受控变量要「锁死」，而不是「记得」

两条支线必须对齐相同优化步数（前 60 步 / 后 40 步）—— 这个约束写进了 config，
由 `30_evaluate.py` 读取并展示，而不是靠人记得。

**而且：变量一旦因故调整，必须同步调整所有臂。**
第 2 轮因预算把步数从 60 降到 40 时，
**A1、B、C 三条臂同时降到 40** —— 绝对水平变了，但**受控关系没变**，结论依然成立。
如果只降了一条臂，整个对照就废了。

### 1.2 防泄漏必须落在内容层面

评测集一旦与训练数据同题，「模型没见过」的前提就破了 —— 所有结论作废。

当时的检查是按 **id** 去重，但实测发现：候选池 300 题里，
**有 12 题与训练池的题面完全相同**（生成器只做了池内去重，id 前缀不同而已）。

**教训**：**防泄漏的检查必须落在内容层面，不能落在标识层面。**
id 是我们自己发的号码牌，**题目内容才是模型真正看见的东西**。

最终做了三层防护：源头去重 → 读池再过滤 → 断言的检查升级为题面级。

### 1.3 闸门必须会「拦人」，不能只会「喊话」

第 2 轮的闸门（要求 L2 ≥ 24 题）判定**未通过**，
但脚本退出码是 0，于是流程照跑不误 —— **闸门只剩一句打印**。

**这是设计缺陷，不是执行失误。** 正确的做法是让闸门非 0 退出。

**但也要承认另一半**：当闸门已来不及拦住（训练钱已经花掉）时，
**正确的动作是「接受事实 + 如实报告」，而不是假装通过。**
本轮就是照实说明「L2 只有 16 题、配对检验样本量偏小、
结论按方向性证据陈述」—— 这比粉饰一个漂亮数字有价值得多。

### 1.4 样本量是设计问题，不是事后能补的

L2 层只有 16 题（要求 24）。这不是"跑多次采样"能解决的 ——
**重复采样只降低采样噪声，而样本量不足降低的是题目层面的代表性。**

当时的估算：「40 题试点命中率 15% × 288 题池 ≈ 43 题」——
看着够，实际扩到 140 题后命中率只有 11.4%，**外推过于乐观**。

**教训**：小样本试点估命中率时，**要按试点本身的不确定性给个区间**，
而不是拿点估计直接乘。

## 二、工程实现

### 2.1 任何「取前 N 条」都要先问：顺序有没有语义

这是坑 21 的正面表述。分块写入的数据（按层、按类别、按批次）
取前 N 条，等于**静默地只取了一个块**。

**可迁移的检查动作**：写下 `[:-N]` 或 `[:N]` 时，停三秒，问：
「这个列表是怎么排序的？顺序携带信息吗？」
如果携带，就该**分层轮转取样**（本项目最终的修法）。

### 2.2 失败必须响亮（fail loudly）

**任何「拿不到结果就当作负面结果」的默认值，都是沉默的数据污染源。**

具体做法（都在项目里落地了）：

- 前置探活（开跑前先 ping 依赖服务，不通直接退出）
- 单条重试 + 连续失败立即中止
- **失败的样本不写盘**，留给断点续跑重试，而不是留下空记录
- 判分器里的 `None` / `0` / `""` 都要先问：**这真的是一次有效测量吗？**

### 2.3 断点续跑要设计进**数据格式**里

本项目的断点续跑不是"记个进度文件"，而是**让每条样本自带唯一键**
`(角色, 题号, kind, 采样序号)`，落盘即完成，重启时按键跳过。

好处：**暂停/恢复、崩溃重启、加题减题，全都自动正确**。
实测：暂停 1 分钟后恢复，自动跳过已完成的 8 题，654 条记录零重复、零损坏。

**代价几乎为零**，收益是"随时可以安全地停"。**这是本项目最划算的设计决策。**

### 2.4 守护/监控进程的判据不能写死

见元规律 2。补充一条实操：**守护进程的收工条件应该写成
「当前所有可能的主流程都不在」**，而不是「某个特定的主流程不在」。

## 三、评测方法

### 3.1 判分口径要单一且可复现

- 所有角色用**同一套** `parse_response` / `answer_equal`
- 筛查采样与评测采样**温度一致**（都取 `eval.sample_temperature`），
  因此筛查结果可以被评测直接复用 —— 省了约 5 小时，且**这不是"将就"，是等价数据**

### 3.2 分层要按「能力边界」分，不是按「难度」分

本项目最有价值的设计是 **L1/L2/L3 的三层定义**：

| 层 | 定义 | 用来回答什么 |
|---|---|---|
| L1 | teacher **会做** | 基准能力 |
| **L2** | **teacher 系统性失败、但 base 有机会** | **核心命题：RL 能否越过 teacher** |
| L3 | teacher 和 base **都全错** | 极限：RL 能否学到全新能力 |

关键在 L2 的定义 —— 它不是"难题"，而是**"老师不会、但学生可能自己琢磨出来"**。
**只有这样的题才能区分「模仿」和「超越」。**
按普通难度分层是分不出这个的。

### 3.3 跨角色比较前，先对齐预算

云 API（DeepSeek V4 Pro）用 1024 token 预算，本机角色用 192 —— 这是**刻意的**：
192 是为「纯 CPU 一条要 40–90 秒」定的上限；云 API 一条几秒，
套用同一上限会造成「被截断的假性低分」。

**后果**：`think=on` 那一栏**不可跨角色横向比较**
（本机角色 192 token 被思考吃光、正文一个字没出，记为 0.0%；
云端有 1024，是 100%）。报告里对这一栏做了加粗标注。

**教训**：看到跨角色的大差距时，**先问是不是预算/口径不对等**，
再问是不是能力差距。

## 四、长任务与流程

### 4.1 先跑探针，再放全量

**CPU 上最贵的失败方式是「跑三小时然后爆内存」。**
所有长流程都先跑小规模探针（`--probe` / `--limit`）拿实测数据，再放开量。

### 4.2 长任务要能停、能续、能查

三件套缺一不可：

| 能力 | 本项目的实现 |
|---|---|
| **能查** | `progress.sh` —— 唯一入口，一屏看完（含按层进度表） |
| **能续** | 数据自带唯一键，落盘即完成（见 2.3） |
| **能停** | `labctl.sh pause/resume` —— 实测无损，释放 12 GB 内存 |

**再加一条纪律**：暂停后要保证**自动巡检不会擅自拉起**
（本项目用 `logs/PAUSED` 标记实现）。否则"暂停"只是幻觉 ——
用户刚腾出机器，两小时后被自动任务重新占满。

### 4.3 后台方式选错会白跑

- `nohup ... &` 在工具托管的环境里**会被会话回收**（本项目踩了 2 次，
  其中一次是跑到第 4 个步骤才死掉，白跑约 2 小时）
- 正确做法：**用工具托管的后台**；或让用户在自己的终端里启动

## 五、文档与协作

### 5.1 改完必须自检 —— 而且要跑工具

| 改什么 | 跑什么 |
|---|---|
| shell 脚本 | `lint_shell.sh`（语法 + `$VAR` 紧跟全角标点的 unbound 隐患） |
| Python 脚本 | `ast.parse`（**不要用 `py_compile`**，会写 `__pycache__` 触发删除拦截） |
| 文档 | `grep -c '^## '` 数标题数 |

**血泪教训**：用章节标题当编辑锚点时，若忘了把它写回去，
**标题会被静默吞掉**（这个错误犯过 5 次）。

### 5.2 不确定就承认，别粉饰

本项目有两个"不好看但必须说"的地方，都如实写进了报告：

1. **GATE-1 未通过** —— L2 只有 16 题，样本量不足
2. **本机推理比云慢 30 倍** —— "本地部署更省"在这台机器上不成立

**诚实报告一个反例，比多一个漂亮数字有价值。**

## 六、如果重做一遍，会改什么

| 序号 | 改动 | 理由 |
|---|---|---|
| 1 | **闸门非 0 退出** | 否则闸门形同虚设（坑 22） |
| 2 | **评测集分层轮转取样，从一开始就做** | 否则静默丢层（坑 21） |
| 3 | **守护判据写成「所有主流程都不在」** | 否则换脚本即失效（坑 23） |
| 4 | **候选池做大 2–3 倍** | L2 只有 16 题，配对检验功效不足 |
| 5 | **暂停/恢复能力在第一轮就建好** | 实测它让"随时可以安全地停"成为可能 |
| 6 | **云基线的 token 预算也记为一张表** | 避免跨角色误读（3.3） |

## 七、最值得带走的三件东西

如果只能带走三件：

1. **数据自带唯一键的落盘设计** —— 让"随时可以安全地停"成为可能，
   代价几乎为零，收益覆盖暂停、崩溃、改题全部场景。（2.3）
2. **按「能力边界」分层** —— L2 的定义（老师不会、学生可能自己琢磨出来）
   才是能区分「模仿」与「超越」的设计。（3.2）
3. **"失败必须响亮"这条纪律** —— 它直接来源于最贵的一次事故，
   而且适用于任何长任务。（2.2）
